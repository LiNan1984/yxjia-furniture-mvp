## 2. 实测方法（这些 bug 是怎么找到的）

不是读代码读出来的，是按顾客的路径点出来的。视口固定 **390×844**（县城老人常用机型尺寸），路径是：
首页 → 上传客厅照 → 选预设 → 立即生成 → 看结果；以及单独问「我想买个沙发」这类 query，看聊天里到底出不出图。

SSE 用 `page.route` + `route.fulfill` 拦掉，不真调模型，一条用例 ~3s 跑完。

### 2.1 四个测量陷阱（这四个我自己全踩过）

1. **量坐标前必须等 CSS 过渡真的播完。** `is-open` 是「先加 class 再播 0.15s」，class 一加上那一帧面板还在屏幕外（实测 `panelTop=634/844`）。所以判据不能是「把手 `top >= 0`」或「`top < innerHeight`」——滑行途中总有一刻满足，随后 `mouse` 起始点落在没升上来的面板上，整条手势静默失效。**等 `getComputedStyle(panel).transform` 收敛到 `none` / `matrix(1,0,0,1,0,0)`。**
2. **「固定栏挡底部」的是 Composer 不是 Tab。** Tab 64px，但 Composer 71px 紧贴在它上面，`#views` 的可见区只到 Composer 顶。任何「主按钮 / 可点 chip 必须在首屏」的断言都以 **Composer** 为基准，以 Tab 为基准会漏 71px。
3. **`loading="lazy"` 的图断言 `naturalWidth` 前必须先 `scrollIntoView`**，否则量到的是 0，会误判成「图全挂了」。
4. **`elementFromPoint` 用视口坐标**：折叠线下面的元素要先 `scrollIntoView` 再取点，否则测的是「在不在屏上」而不是「有没有被盖住」。

## 3. 五个 bug

### ① 聊天里永远出不了家具图卡

- **顾客看到的**：问「我想买个沙发」，阿杏回一段文字 + 「猜您还想问」，一张家具图都没有。
- **根因**：`src/axing/js/chat-core.js` 的 `tryStream` 把 handlers 包了一层，写的是
  `onTool: (n) => handlers.onTool && handlers.onTool(n)`——**只透传了名字**。而后端 SSE 的 `tool` 事件第二个参数就是商品数组（含 `image`），商品在这一层被整包丢掉。
  前端 `api.js` 本来是老实透传的（`handlers.onTool(ev.name, ev.products)`），坏在中间这层位置式包装。
- **修法**：`onTool: (n, products) => handlers.onTool && handlers.onTool(n, products)`
- **状态**：已修，commit `eeb52d0`，已上线。
- ⚠️ 注释里留了「第二个参数是工具返回的商品数组（含 image）」——**位置式包装只透传第一个参数是个悄悄坏掉的写法**，下次再加 `onXxx` 包装一定把实参数清楚。

### ② 商品卡排到追问 chips 后面

- **顾客看到的**：家具图夹在正文和「猜您还想问」中间，看起来图像是追问的一部分。
- **根因**：`appendProductCards` 是 `async function`，外覆的 `div.ax-chat-products` 要等 `await loadUi()` 之后才 append；而调用方 `appendAi` 是**同步**的、追问 chips 也是**同步**追加的。同步追加的 chips 就排到了异步追加的卡片前面——**兄弟节点的显隐先后由追加先后决定，不是由代码书写顺序决定。**
- **修法**：改成「同步 append 空壳占位 → 异步填卡片 → 一张都没成再 `remove()` 空壳」。空壳那一手同时解决了「填卡期间气泡里出现一道带 margin 的空白缝」。
- **状态**：已修，commit `eeb52d0`。
- ⚠️ 判据在 `tests/axing-product-card-ratio.test.js` 的 C2 后半段，**别改回去**。

### ③ 竖图把卡片顶歪

- **顾客看到的**：列表里突然有一张卡比别的卡高一倍多，两列网格错行。
- **根因**：`.p-card__img img` 缺 `position:absolute`。`<img>` 留在文档流里就会参与父级的内容高度计算，**它自己的内在宽高比会压过父级的 `aspect-ratio`**；`object-fit:cover` 只能裁切内容、救不了盒子本身。
- **实测数字**：768×1152 的竖图把对话卡片顶到 **374px**（横图 156px），商品页两列网格顶到 **212px**（横图 141px）。
- **修法**：`.p-card__img img{position:absolute;inset:0;width:100%;height:100%;object-fit:cover;}`
  让 `<img>` 退出内容高度计算，盒子高度只由 `aspect-ratio` 决定。无图分支的 `skeleton()` 本来就是 `position:absolute`，这样两条形态也一致了。
- **状态**：已修，随 `af35c7c` 上线。

### ④ 首页「拍照试摆」磁贴把顾客扔进全屏上传页

- **顾客看到的**：同一个首页，上面那张「上传客厅照」卡点下去是底部浮窗，下面四宫格的「拍照试摆」点下去变成一整个上传页——**同一个首页两种行为**。
- **根因**：那个磁贴写的是无条件 `goView('view-upload')`，而别处上传入口全是
  `(ctx.openUpload ? ctx.openUpload() : ctx.go('view-upload'))`。违反交互规范 §1-2 原话：「#view-upload 不作为独立全屏 view 存在。上传能力收进底部浮窗。」
- **修法**：**不是改那行代码，是把整个四宫格删掉**（commit `eab904c`）。入口少一处，就少一处能不一致的地方。
- **状态**：已修并上线。
- 回归测试 `tests/axing-upload-entry.test.js` 刻意**枚举当前页面上真实存在的入口**而不是写死清单：四宫格被删它就少测一项（不会假红），哪天又被加回来且路线写错，立刻现形。

### ⑤ `bed` 品类的默认示例房图是个 404

- **顾客看到的**：卧室品类「没照片？用默认客厅图体验一下」被前端探测禁用，点不出来，卧室失去「没照片也能试」的路径。
- **根因（两层）**：
  1. `src/server.js` 的硬编码兜底表写 `defaultRoom: '/images/default-room-bed.jpg'`，**这个文件从不存在**（`src/images` 里只有 `default-room.jpg` / `default-room-real.png`，真正的卧室图是 `bed-double.jpg`）。
  2. server 有一段「`!fs.existsSync(CATEGORIES_FILE)` → `fs.writeFileSync(兜底对象)`」的同款逻辑（`SCENE_STYLES_FILE`/`CATEGORIES_FILE`/`FEATURE_FLAGS_FILE`/`PRESETS_FILE` 都有），**首次启动就把兜底值落盘进 `data/*.json`**。而 rsync 从不同步 `data/` → **坏值在生产永久固化，改 server.js 也治不了已经落盘的旧文件。**
- **修法（分两半，别只做一半）**：
  - **已做**：改 `server.js` 兜底表 → `/images/bed-double.jpg`。治的是新装 / 数据文件丢失。
  - **待店主做**：生产 `data/categories.json` 里那个值**已经被固化**了 → 后台 `/admin/categories` 手动改。
- **状态**：代码侧已修；**生产数据侧还没修，只有店主能点。**
- ⚠️ 接手人别误判成「再部署一次就好了」——rsync 不碰 `data/`，部署一百次那个值还在。这是本次唯一遗留的线上问题。

## 5. 顺手修掉的第 6 个问题：测试端口撞车（会造成安静的假绿）

- **现象**：`axing-category-images.test.js` 和 peer 会话的 `axing-tryon-enabled.test.js` **都写 `PORT = 3534`**。
- **为什么这不是「反正 `--workers=1`」**：顺序跑时两个文件各起各杀，确实不炸。但只要**并行跑一次**、或者**上一次的进程没退干净**，第二个实例的 `waitServerReady()` 会被**第一个实例**应答通过 → 它全程在跟别人的 server 说话：跑得完、报全绿，但验的压根不是本文件起的那个进程。
  **不报错、不超时，只是悄悄测错对象**——这是这棵树上最贵的一类假绿。
- **修法**：① 我的文件搬到 **3536**；② 加起飞前守卫 `assertPortFree()`：spawn 之前先 fetch 一次，端口上已经有东西应答就直接 throw，把安静的假绿变成响亮地红。
- **反向验证（今天实测）**：在 3536 上起个假服务 → 测试红，报错文案就是「端口 X 在我 spawn 之前就已经有服务在应答了……别直接放过去（会变成安静的假绿）」；杀掉假服务 → 恢复 2 passed。
- ⚠️ **这个守卫目前只加在我这一个文件里。** 其余约 20 个测试文件各自 spawn 自己的端口，都没有守卫。要根治得逐个加，或抽一个共享 helper——但那要碰 6 个 peer 会话正在编辑的文件，本轮刻意不做。
  **接手建议**：下次碰哪个测试文件，就顺手把 `assertPortFree()` 加进哪个。新写测试文件照 3536/3550 的样式直接带上。

## 6. 生产现状（怎么核实的：没 SSH 也核得动）

当时生产 SSH 凭据被服务端拒：HTTP 3300 一直 200、22 端口 `nc` 通、banner 正常、服务端也确实走了密码认证流程，但最终 `Permission denied (publickey,password)`。判断是凭据不对，**没有再密集重试**（连打会触发服务端 fail2ban，越锁越久），改为全程只读 HTTP 核对。部署本身由会话 `yxjia-mvp-9f` 完成。

核实结果（只记技术事实，不记经营数字）：

- 商品卡图逐个 fetch 全部 200（含那张 768×1152 的竖图 `/images/sofa-tihua.jpg`）。
- 所有 `.p-card__img` 容器高度一致 = **141px**，没有竖图把某一张顶高 → bug ③ 线上已生效。
- `/api/categories` 里 `bed` **仍指向 404** → §3-⑤ 那条"只有店主能点"的待办仍然挂着。
