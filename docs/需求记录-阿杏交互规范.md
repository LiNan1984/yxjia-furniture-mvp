## 1. 实测确认的问题（2026-10-05，端口 3400）

用 Playwright 打了 4 组探针，逐条坐实（非猜测）：

| 编号 | 现象 | 实测证据 | 根因 |
|---|---|---|---|
| **P1** | `#view-upload` 是多余的全屏页 | 首页上传卡点进去是一个完整 repeat 页：`sec-eyebrow / sec-title / sec-desc / stage / 拍一张客厅照 / 从相册选择 / 重新拍照 / 直接去试摆 / 示例房间` | 首页卡与独立 view 双入口，同一件事两个全屏 |

| **P3** | 点「你可以这样问」chip 只有用户气泡，永远没有回复 | chip 点击后 `/api/chat/guide` 请求数 **0**，时间线只有 `user:现代简约沙发` | `view-home.js:201` 的 chip 只 `ctx.appendChat('user', text)`，没走 Composer 的 `send()` |

- **流式通道**：`/api/chat/guide/stream`（SSE）+ `/api/chat/guide/status` 已在 `server.js` 里。

## 2. 需求判定

### 必做（本轮）

| ID | 需求 | 对应问题 |
|---|---|---|
| R1 | 聊天是**常驻对话**：任何页面发消息都能看到自己那条 + 阿杏回复，并自动回到对话流 | P2 |
| R2 | 删除 `#view-upload` 独立全屏页，上传改成**底部浮窗**（喜豆 spec §1-2：底部推入 0.15s、最高 724px、超出滚动、蒙版/下拉取消） | P1 |
| R3 | 「你可以这样问」chips **真实发送**：点一下 = 用户发一句话 = 走完整问答链路；并沉到首页底部 | P3 |
| R4 | AI 回答**全量 Markdown 渲染**（标题/列表/引用/代码块/表格/粗斜体/行内代码/链接/分割线），且流式增量渲染 | P4、P9 |
| R5 | 所有「阿杏产出的卡片」左边都有阿杏头像 | P5 |
| R6 | 右上角极小字：`打给店里 13359140982`（可点 tel:）+ `银杏家具体验店 · 柞水县乾佑街道农机路河西` | P6 |
| R7 | 气泡带时间戳（对齐参考图 09:41/09:42） | P7 |
| R8 | 生成中可「停止生成」（喜豆 spec §1-11 场景二） | — |
| R9 | 修 `default-room-bed.jpg` 404 | P8 |
| R10 | 按 `喜豆AI银行交互规范.pdf` 产出《阿杏交互规范》 | 用户第 4 点 |

### 明确不做（避免范围膨胀）

- 不做「下拉加载历史对话」（喜豆 spec §1-5 自述「技术不支持：数据从哪来、怎么存、怎么管理」；MVP 无账号体系，`data/users.json` 只是手机号白名单）。
- 不做语音全双工 WebSocket 接管 Composer（喜豆 spec §11「语音不离开 Chat」是远期；MVP 保留全屏 `view-voice`）。
- 不引任何前端框架 / CDN / 新 npm 运行时依赖（CLAUDE.md 铁律）。
- 不改后端 Agent 的模型选型与工具集（已满足 agents-sdk skill 的 "start with one agent / add tools deliberately"）。
- 不重写 `view-3d` 的 three.js 舞台（WebGL 已就位，本轮只碰聊天链路）。

## 3. 落地顺序（依赖约束）

```
markdown.js（零依赖叶子模块）
   ↑
chat-core.js（常驻聊天中枢，消费 markdown.js）
   ↑                        ↑
chat-composer.js（改）   index.html + axing.css（契约）
   ↑                        ↑
   └────── app.js（壳：路由 + 浮窗 + chat 层挂载）──────┘
                              ↑
              view-home / view-upload / view-voice / ui / api（各自按边界改）
```

**markdown.js 必须先落**——它是叶子、无依赖，同时又被 chat-core / view-voice / ui 三处消费，契约不先定死会返工。
