## 1. 顾客痛点 Top 3

### 顾客痛点 1（升为首位）：想买床的顾客，首页无货、试摆也用不了
- **描述**：老板已进 11 张床的实拍，但线上货架 0 张床（仅 3 款沙发）；即便 `bed-1` 混在货架里，试摆的 prompt/文案/默认客厅图/预设**全部写死"客厅+沙发"**，"把床搬回家"这条路走不通。
- **证据**：线上 /api/products 只有 3 沙发；server.js 2649/2778/3152/864-893/852-853 硬编码客厅/沙发文案；presets.json 5 条全提客厅/沙发；DEFAULT_ROOM_URL 只有客厅图（index.html:721）。
- **商业损失**：床是家具店客单价与复购都高的品类；只能看沙发体验、买床只能干看图，等于**把最需要"摆回家看看"的品类做成了最没有体验的品类**。

### 顾客痛点 2（新）：货架又少又"顶格"——首页最多露 6 款，多上的货顾客根本看不见
- **描述**：`renderCatalog()` 写死 `.slice(0,6)`（index.html:606-626），沙发板块只能摆 6 张；即便把 11 张新沙发入进去，绝大多数也进不了顾客视野。
- **证据**：index.html:606-626；`.products` 网格 3 列固定。
- **商业损失**：老板拍的每一张新沙发都是成本，看不见=零转化；品类越多，"顶格 6 款"的浪费越大。

### 顾客痛点 3（延续 v2，观察位）：买前"回家变丑怎么办"无人回应；试摆本可解，却还带 2 个 bug
- **描述**：试摆正是"摆回家看看"的正解，但 ①登录上传文件必 400、②兜底图 404——**顾客最可能用的那条路径自己断了**。
- **证据**：见第 0 节两个实测断点。
- **商业损失**：v2 洞察里"最后 1cm"的顾虑依旧没被跨越，且现在是"能解的工具却在报错"，比没有更伤信任。

## 2. 老板痛点 Top 3

### 老板痛点 1（首位）：每进一批货都要手工逐张点，且没有能复用的入库工具
- **证据**：现成只有 `/api/admin/upload-and-identify` 逐个传（server.js:2442），products.json 是"读-改-写"追加且**非原子**（2474-2501），并发会互相覆盖；批量脚本 spec-v1 就推迟了、至今没有。现在又压了一批 data/new(23 张)。
- **损失**：老板每次拍照上新都要机械劳动；机械劳动越多，货架更新越慢、线上越留不住人。
- **长远判断**：库存会一批批来，**一个"严格串行、可重复跑、可跳过已存在"的小入库工具**是从长远最省老板时间的单点投入（还顺手补上当年欠的脚本债）。

### 老板痛点 2（新）：品类多了，后台却管不了"品类"
- **证据**：products.json 无 category；后台商品编辑弹窗（products.html:86-98, 193-201）**没有品类输入**，只有 AI 上传页能设，且设的是英文塞 JSON；另有上传路径把中文品类塞进 subtitle（server.js:2262 + admin/product.html:46）。三套词表互不兼容。
- **损失**：品类一多就成了糊涂账；将来按品类编辑/上架/统计数据全都无从下手。
- **长远判断**：`category` + 板块配置是**所有未来品类（柜/桌/椅/餐厅…）的地基**，v3 打地基比以后再补便宜一个量级。

### 老板痛点 3：线上还停在 3 款沙发，和本地脱节
- **证据**：线上 /api/products = 3（全沙发）；本地 7。核心手工商品（sofa-1 等）疑似在线上又被覆盖/未同步。
- **损失**：线上是顾客唯一入口，货架旧=顾客看到的店是旧的。
- **长远判断**：v3 部署时必须以"覆盖前备份 + 合并不覆盖"为硬线（CLAUDE.md 第 9 节踩过的坑），并把本地 7 款 + 新入库品类作为唯一事实源推到线上。

## 3. v3 功能建议（一句话：从单品货架 → 多品类家具体验）

### 主线 A：品类/板块地基（一切的根，必须先做）
- 商品补 `category` 字段（英文 id：sofa/bed/cabinet/table/…，与 server.js 既有白名单 2408 对齐），新增 `data/categories.json` 板块配置（对齐 presets/scene-styles 先例，未来 `/admin` 可编辑），首页从"写死 6 款"改为**按板块循环渲染**（去掉 `.slice(0,6)`）。
- **为什么是它**：它同时解顾客痛点 2（货架不再顶格）、老板痛点 2（品类可管）、顾客痛点 1 的前置（床要能作为独立板块）。**从长远看，这是"再来 10 个品类也不用改首页结构"的唯一做法。**

### 主线 B：沙发扩容 + 把床搬回家（两个板块的内容 + 体验）
- 沙发板块：把 `data/new/沙发`（11 张）入库成在售沙发（AI 命名），数量不再顶格。
- **卧室板块（新）**：把 `data/new/床`（11 张）入库成床；**把试摆从"沙发/客厅"通用化**——默认 prompt、预设、默认房间图、文案都按 `category` 走（`sceneRoomForProduct` 已预留 `bed→卧室`，补活它），让"把床搬回家"与"把沙发搬回家"同一套机制、同一批预设、各自默认房间图。
- **为什么是它**：床是本次唯一新增品类，也是"最需要摆回家看"的品类；复用已验证的 gpt-image-2 合成链路，**不新增模型/依赖**，改动集中在 prompt/文案/默认图/板块渲染。

### 配套：可复用串行入库工具 + 3 个顺手修
- **入库工具**（主线 A/B 的数据前提）：严格串行、可跳过已存在、失败续跑；默认新入库品 `status="下架"` 待老板审（沿用 spec-v1 定性）。这直接回答老板痛点 1，也回答了"是不是又上传 skill"——**结论是没有现成 skill，所以这次把它做成一个能反复用的小工具**。
- **顺手修（都在旗舰试摆链路上，属必修）**：①修 index.html:810-811 登录上传文件不带 sofa 字段必 400；②补回落图（sofa-zhongshi.jpg 已删）或改指向未删图；③部署前把本地 7 款合并推线上（不覆盖）。

### 明确不做（YAGNI，避免 v3 摊子过大）
- **不做**异步任务队列（沿用 spec-v2 决策 2，同步 + 前端计时器）；**不做**场景图失败兜底 demo 图（spec-v2 决策 3 的诚实性硬线照搬）；**不动** spec-v2 的 scene-image 场景图工厂本体（那是 v2，v3 只确保它测试落定不回退）；**不引**任何新依赖/新模型；**不碰**阶跃图像模型；**不做**柜/桌/餐厅板块（地基留好，内容下一轮）；**不做** git commit（团队规则：改动留工作区给老板审）。

## 4. 给产品角色 P 的交接

1. **v3 主菜顺序**：先主线 A 地基（category + categories.json + 首页板块循环），再主线 B（沙发扩容入库 + 卧室板块 + 试摆通用化），配套入库工具贯穿 A/B。三块尽量能独立合入、可分别回滚。
2. **硬线**：入库严格串行（products.json 追加非原子，见 server.js 2474-2501）；零新依赖；两色调 + 无前端框架 + 老人友好 + 无数据库全遵守；category 用英文 id、中文名放板块配置层，别把中文品类塞 subtitle。
3. **验收一句话**：首页出现"沙发板块"（≥10 款、不再顶格 6）和"卧室板块"（床可逛）；顾客能"把床搬回家"合成（默认卧室图 + 品类感知 prompt），也能继续"把沙发搬回家"，两个 bug 不再复现；后台能看懂并能改品类。
4. **给 T 的提醒**：试摆通用化测"同机制两品类"（沙发→客厅默认、床→卧室默认）；category 渲染测"有/无 category 的商品都不报错"；首页去 slice(0,6) 测"≥10 款全露出"；入库工具测"串行不并发、跳过已存在、新品默认下架"；2 个 bug 各加一条回归。
5. **交给老板的两处决策**（spec-v3 里标注，不阻塞开发）：①data/new 的"未命名.png"等疑似非商品图要不要入库（建议：跳过/单独放）；②线上 3 款与本地 7 款的合并以哪份为准（建议：本地为唯一事实源，覆盖前备份）。
